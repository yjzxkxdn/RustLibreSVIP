# Design notes

The port keeps the Python architecture so behaviour can be diffed mechanically.

## Crates

| crate | responsibility |
| --- | --- |
| `libresvip-core` | internal project model (`Project`/`Track`/`Note`/curves), tick maths, `TimeSynchronizer`, settings + YAML emitter, option schemas, plugin traits, gettext catalogs, text/binary helpers |
| `libresvip-plugins` | one module per format identifier, compiled in (no dynamic loading) |
| `libresvip-middlewares` | the six middlewares, same order as the Python loader |
| `libresvip-cli` | typer-compatible command surface, rich-compatible output |
| `libresvip-gui` | egui/eframe rebuild of the Qt Quick desktop GUI: immediate-mode layout mirroring `converter_page.qml`, custom Material widgets, the same task/conversion flow |
| `libresvip-web` | `wasm32-unknown-unknown` entry point: no wasm-bindgen, no WASI, a C ABI over `alloc`/`convert`/`result_*` driven by `web/index.html` |

## Model fidelity

Python models are pydantic v2 with `populate_by_name=True` and camelCase
aliases. Rust structs therefore:

* `#[serde(rename = "Alias")]` for output and `#[serde(alias = "snake_case")]` for
  input, in the exact declaration order of the Python class,
* `#[serde(default)]` with a hand-written `Default` where pydantic defaults are
  non-trivial (`Volume = 1.0`, `SongTempo.bpm = 120.0`, `Phones = -1.0`, …),
* `Option<T>` fields serialised as `null` (no `skip_serializing_if`),
* `ParamCurve` has a manual `Serialize` so `TotalPointsCount` is always the
  current length (`{"PointList": [...], "TotalPointsCount": n}`),
* `Track` is an enum with a manual serde implementation so the discriminator is
  read from `Type` (alias `type_`) exactly like pydantic's tagged union.

Numbers are coerced leniently on input (`model/serde_util.rs`) to mirror
pydantic's non-strict mode. Rounding always uses `f64::round_ties_even`, matching
Python's `round()`.

## Options as data

The CLI needs to prompt for plugin options and to print `plugin detail`, both of
which rely on pydantic reflection in Python. In Rust each plugin returns a
`Vec<OptionFieldDef>` describing every field (key, title, description, kind,
default, choices) in declaration order; `OptionKind::Enum` carries the enum
member names, values and translated titles, and `default_repr` reproduces
Python's `str(enum_member)` output (`PlusHandlingMode.AUTO`).

## CLI output

* Tables reproduce `rich.table.Table`'s layout: natural widths, shrinking of
  wrappable columns (equal share, leftover to the narrowest column), border and
  padding rules, and per-cell `divide_line` + `rstrip_end` + `truncate(width,
  "ellipsis")` with the same character-vs-cell-length quirks.
* Prompts reproduce `rich.prompt` (choices/default rendering, validation
  messages, wrapping at the console width).
* Parameter errors reproduce typer's `Usage:`/`Try …`/`Error` panel byte for byte.
* Translations come from the real `.mo` catalogs, merged like
  `get_translation()` (core first, then every plugin, then middlewares).

## Settings

`settings.yml` is read with permissive typing and written with a PyYAML-compatible
emitter (sorted keys, block style, `!!python/object/apply:pathlib.WindowsPath`
path tags). The parity harness compares the file byte for byte after
`conf set language`.

## Verification

* `crates/libresvip-core/tests/core_cases.rs` — differential vectors generated by
  `scripts/gen_core_cases.py` (tick maths, time sync, curve sampling, project
  transforms).
* `crates/libresvip-plugins/tests/golden.rs` — per-plugin byte comparison of dumps
  plus semantic comparison of loaded projects, fed by `scripts/gen_golden.py`.
* `scripts/check_parity.py` — CLI stdout/stderr/exit-code diff plus settings
  round-trip for all commands, including interactive conversions.
